# 운영 장애 분석 두 건

> 2026 · 광섬유 센서 관제 시스템(Go) · 역할: 원인 분석, 수정, 실기 검증

두 장애는 같은 날 같은 조건(50km, 2채널)에서 함께 나타났습니다. 처음에는 하나의 원인으로 보였지만, 실측으로 서로 다른 문제임을 가려냈습니다.

---

## 1. 프로세스가 로그 없이 꺼지는 문제 → 98GB OOM

### 증상
50km 설정으로 수집을 시작하면 2분쯤 뒤 앱이 아무 로그 없이 종료됐습니다.

### 진단
`GODEBUG=gctrace=1`로 GC 로그를 켜고 재현했습니다.

```
gc3  @10.459s   …  32 MB  (수집 시작 직후)
…
gc21 @135.785s  …  98 GB
fatal error: out of memory   (Windows VirtualAlloc 실패)
```

살아 있는 힙이 135초 만에 32MB에서 98GB로 늘었습니다. 크래시 스택은 임계값 이벤트 생성 → 이벤트 직전 구간 프레임 복사 → 메모리 할당 실패로 이어졌습니다.

### 원인
임계값 설정 파일에 0.0 값이 들어 있어, 전 구간에서 매 사이클 이벤트가 대량으로 생성됐습니다. 이벤트마다 직전 프레임과 FFT 스냅샷을 복사하므로 메모리가 기하급수적으로 늘었습니다.

### 배운 점
GC가 있는 언어에서도 **상한 없이 쌓이는 설계**는 막아주지 못합니다. 이후 만드는 코드에서는 큐·구독자·이벤트 버퍼에 상한을 먼저 정합니다. → [samples/event-ingest-spring](../samples/event-ingest-spring)의 구독자 상한

## 2. 장시간 수집 중 리소스 부족 오류(553)

### 증상
약 96초 정상 수집 후 버퍼 오류 → 복구 시도 → `ApiInsufficientResources(553)` 10회 연속 → 수집 중단.

### 가설과 검증

| 단계 | 내용 |
|---|---|
| 가설 | 디지타이저 SDK 문서상 553의 대표 원인은 "DMA 버퍼가 너무 많거나 큼" |
| 계산 | 버퍼 크기 상한 16MB × 버퍼 32개 = 고정 DMA 메모리 약 **512MB** (레거시 C는 같은 조건에서 약 38MB) |
| 1차 시도 | 버퍼 수를 16으로 줄였으나, 같은 날 위 OOM이 크래시 원인으로 확정되면서 미검증 상태로 되돌림 |
| 재현 | 몇 주 뒤 **임계값 판정을 끈 상태에서도** 553이 재현됨 → OOM과 별개의 독립 문제로 확정 |
| 수정 | 버퍼 수 32 → 16, 고정 메모리 512MB → 256MB. FFT 해상도는 버퍼 크기에서 오므로 영향 없음 |
| 회귀 확인 | 버퍼 수를 줄이면 큐 여유가 531ms → 266ms로 줄어 짧은 거리·고속 설정에서 오버플로 위험이 있음 → 5km 설정으로 오버플로 오류(582) 없음 확인 |

### 배운 점
두 증상이 같은 시점에 나타나도 원인이 하나라고 단정하지 않습니다. 한쪽 원인을 꺼 둔 상태에서 재현해 보는 것이 가장 확실한 분리 방법이었습니다.

## 3. 운영 배포 후 오탐 원인 분석

배포 당일, 지나가는 차량이 장비(브레이커, 신뢰도 0.971)로 웹에 등록됐습니다. 로그를 따라가 보니 두 가지 결함이 겹쳐 있었습니다.

- 이벤트 지속시간 단위 버그로 짧은 이벤트가 500초 이상으로 계산됨
- 이동체(차량)로 판정한 뒤에도 분류기로 전송이 계속됨

두 가지를 고치고 원인 분석 보고서를 남겼습니다. 이 사례를 계기로 판정 구조 자체를 다시 설계했습니다 → [알림 판정 품질 개선](03-alert-quality.md)
